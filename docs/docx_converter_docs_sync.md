## Контракт OcrProvider

`pdf_core.py:16-20`, дословно:

```python
class OcrProvider(Protocol):
    """Интерфейс OCR-провайдера: скан-PDF (bytes) -> markdown."""

    def ocr_pdf_to_markdown(self, pdf_bytes: bytes,
                            page_range: str | None = None) -> str: ...
```

Единственная реализация — `OcrmypdfProvider` (`pdf_core.py:23`). `page_range`
имеет умолчание `None`, то есть реализации обязаны принимать вызов и без него.

## Как вызывается OCR-тракт

```
app._convert_uploaded_file (app.py:245)
  └─ pdf_core.pdf_to_markdown_with_status(bytes, page_range=…, mode=…)
       → (str, dict | None)
```

Сигнатуры (`pdf_core.py:43`, `pdf_core.py:84`):

```python
def pdf_to_markdown_with_status(pdf_bytes, *, page_range=None, mode="auto",
                                provider=None) -> tuple[str, dict[str, Any] | None]
def pdf_to_markdown(pdf_bytes, *, page_range=None, mode="auto", provider=None) -> str
```

Аргумент `provider` из UI **не передаётся никогда** — `app.py` зовёт функцию
только с `page_range` и `mode`. Единственные потребители протокола на момент
аудита — тесты (`tests/test_pdf_core.py`). Поэтому подключение нового
провайдера к UI — отдельный этап 8, а не побочный эффект этапов 01–07.

`ocr_auto_mode.py` протокол провайдера не использует вообще: слов `provider` и
`Protocol` в файле нет. Этап 1 его не трогает.

### ПРАВКА #73: MinerU из UI (этап 8)

У `ocr_mode` три значения: `off`, `auto`, `mineru`. `auto` (OCRmyPDF) попадает
в переключатель, только если `check_ocr_dependencies` нашёл все три бинарника
(`app._ocr_mode_options`, проверка кэшируется на процесс) — на Streamlit Cloud
их нет, и вариант там не предлагается. Для PDF в режиме `mineru`:

```
app._convert_uploaded_file(…, ocr_mode="mineru", verify=…, annotate=…, status=…)
  ├─ app._pdf_page_subset(bytes, page_range)      # pypdf; run_pipeline диапазона не знает
  └─ ocr.cli.run_pipeline(bytes, source_name=…, work_dir=<tmp>, verify=…, annotate=…,
                          cache=LocalCache(app._OCR_CACHE_ROOT),
                          provider_factory=app._mineru_provider_factory(key, status))
       → (markdown, report)
```

- `run_pipeline` и весь `ocr/` **не менялись**. Прогресс (`st.status`) снят со
  швов провайдера: подкласс `MineruProvider` в фабрике метит `fetch_raw_zip`
  («загрузка» → «постобработка и проверка»), инжектируемый `sleep` — «ожидание».
  Отдельного колбэка прогресса в тракте нет; постобработка и проверка идут
  одной меткой (это миллисекунды).
- Ключ: `st.secrets["MINERU_API_KEY"]`, затем переменная окружения
  (`app._mineru_api_key`). При попадании в кэш ключ не нужен.
- Кэш — `LocalCache` в `.cache/ocr` рядом с `app.py`; на Streamlit Cloud он
  эфемерный, это осознанно. `make_cache("drive")` по-прежнему не реализован.
- Номера страниц в находках при заданном диапазоне считаются **от вырезки**,
  а не от исходного PDF (UI об этом предупреждает).
- `MineruError` показывается текстом ошибки, `MineruAuthError` — с подсказкой
  про ключ; трейсбека в UI нет (`result["error"]`).
- В результате конвертации новый ключ `report` (`None` вне режима `mineru`);
  `report.json` скачивается отдельной кнопкой, в общий ZIP не входит.
- Тесты — `tests/test_app_fixes.py`, с фейковым провайдером, без сети. Живой
  прогон MinerU из UI этой правкой **не проверялся** (сети не было): проверены
  путь через локальный кэш на `_test/fixtures/ocr/bakeoff.pdf` и ветка ошибки.

## ocr_converter.py и новый тракт

`ocr_pdf_to_searchable_pdf` — PDF → searchable PDF через `subprocess`
(`ocrmypdf --skip-text --deskew --rotate-pages -l rus+eng`), плюс
`check_ocr_dependencies`. Markdown модуль не производит, в сеть не ходит, кэша
и отчёта у него нет. Оба вызова ограничены по времени: `OCR_TIMEOUT_SEC = 300`,
`DEPENDENCY_TIMEOUT_SEC = 15`.

**Новый тракт его не дублирует и не заменяет.** `ocr_converter.py` остаётся
оффлайн-движком за `OcrmypdfProvider` (в CLI — `--engine ocrmypdf`), MinerU
встаёт рядом вторым провайдером. Файл в автономном прогоне не правится.

## convert.py и сырая HTML-таблица

Прогон: заголовок `## ТЕХНИЧЕСКОЕ ЗАДАНИЕ` + первые 600 символов первого
`<table>` из `vlm.md` (теги закрыты вручную) → `convert_md_to_docx(md, out,

Результат: **таблица не появилась** — `len(document.tables) == 0`. Весь
фрагмент лёг одним абзацем текста **вместе с тегами**: в тексте абзаца
присутствуют подстроки `<table>`, `<tr>`, `<td>`. Исключения не было.

Вывод для спеки 04: HTML-таблицу из выдачи MinerU обязан разобрать
постпроцессор — до `convert.py` она доходить не должна. Неразобранная таблица
поэтому и стоит правилом `html_table_unparsed` с серьёзностью `critical`.
`convert.py` при этом корректен и не правится: он никогда не заявлял поддержку
сырого HTML.

## Метрика vlm→golden

`VLM_TO_GOLDEN_DIFFS = 76` (ПРАВКА #68; до неё — 12). Расчётное значение в
спеке — 14; **эталон под число не подгонялся**, расхождение объяснимо и
относится к метрике, а не к `golden.md`.

Полный список опкодов `difflib.SequenceMatcher` по `text_tokens`:

| # | Было | Стало | Правка |
|---|---|---|---|
| 1 | `Noп/п` | `№` `п/п` | 1 |
| 2 | `No1` | `№` `1` | 1 |
| 3 | `сыручими` | `сыпучими` | 4 |
| 4 | `$C^{\circ}$` `;-` | `°C;` `-` | 2 + 8 |
| 5 | `$C^{\circ}$` `.` | `°C.` | 2 |
| 6 | `РоЕ` `IR-камерами` | `PoE` `IP-камерами` | 3+5 |
| 7 | `РоЕ;-` | `PoE;` `-` | 3 + 8 |
| 8 | `No384-ФЗ,` | `№` `384-ФЗ,` | 1 |
| 9 | `No7-ФЗ«Об` | `№` `7-ФЗ«Об` | 1 |
| 10 | `A.II.` `Taipov` `P.P.` `Hypeeb` `A.P.` | `А.Ш.` `Таипов` `Р.Р.` `Нуреев` `А.Р.` | 6 |
| 11 | `A.III.` | `А.Ш.` | 6 |
| 12 | `E.K.` | `Е.К.` | 6 |

Причина расхождения 12 против 14 — **опкод 10**. Расчёт исходил из пяти
отдельных опкодов на пять строк блока подписей, но `text_tokens` снимает
переводы строк, и подряд идущие изменённые токены трёх строк (`A.II. Taipov`,
`P.P. Hypeeb` и инициалы `A.P.`) склеиваются в один опкод: первый неизменённый
токен между ними — только фамилия `Сиражитдинов`, стоящая уже после `A.P.`.
Три ожидавшихся опкода схлопнулись в один, 14 − 2 = 12. Остальные одиннадцать
совпали с расчётом один в один, включая предсказание, что склейка трёх
`<table>` в одну pipe-таблицу опкодов не даёт (разметку `text_tokens` снимает).

### ПРАВКА #68: 12 → 76

Правка 8 сборки эталона («;-» и «:-» → «; -» и «: -») разводит 66 склеек на два
токена. 64 из них дают собственный опкод; две попали внутрь уже существовавших
соседних — это опкоды 4 и 7 в таблице выше, их правая колонка поэтому стала
двухсоставной. 12 + 64 = 76. Списки опкодов до и после сверены поштучно:
ни один из двенадцати прежних не исчез и новых, кроме склеек, не появилось.

Остаток тракта на эталоне (`REMAINING_DIFFS` в `tests/test_ocr_postprocess.py`)
от правки 8 не зависит и равен 5: «сыручими», «IR-камерами» и три опкода на пяти
подписях. Порог там опущен с 7 до факта — запас в две единицы пропускал бы
регрессию на один опкод.

## История коммитов: почему #74–#78 одним коммитом (2026-09-20)
