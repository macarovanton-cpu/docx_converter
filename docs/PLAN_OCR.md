# План реализации OCR-тракта MinerU в docx_converter

Статус: этапы 0–8 и этап A выполнены (#60–#83); этап B — в работе, спеки 13–16 (#86–#91); сверка по картинке
подключена к тракту (#91), живая проверка — за человеком; UI — спека 17.
Исполняется по спецификациям в `docs/specs/ocr/`.

## Цель

Точка подключения для ИИ-агента (Hermes Agent) и для человека в Streamlit:
на входе тендерный PDF (часто скан), на выходе качественный Markdown со
структурой плюс машиночитаемый отчёт о сомнительных местах.

Главное требование: не менять смысл исходника. Особо критичны цифры,
единицы измерения, ГОСТ/ТУ, марки оборудования, реквизиты, таблицы.
Тракт чинит только известные систематические артефакты OCR; всё
сомнительное помечает, а не исправляет.

## Сквозной пайплайн

    PDF ──► [1] Кэш? ──нет──► [2] MinerU vlm ──► сырьё в кэш
                    └─да─────────────────────────┘
                                                 │
            [3] Постпроцессор ◄──────────────────┘
                    │
            [4] Валидатор ──► report.json
                    │
            [5] (--verify) MinerU pipeline ──► diff ──► + в report.json
                    │
            out.md  +  report.json  +  (--annotate) пометки в out.md
                    │
            Hermes / человек / convert.py → DOCX

1. Кэш. sha256 файла. Если PDF уже распознан — сырой ответ MinerU
   берётся из кэша, в облако ничего не уходит.
2. Распознавание. PDF отправляется в MinerU cloud API, режим `vlm`,
   `language=east_slavic`, `is_ocr` по наличию текстового слоя. Ответ —
   zip: `full.md` (таблицы в HTML), `content_list.json` (блоки с номерами
   страниц), картинки. Сырьё кладётся в кэш как есть.
3. Постпроцессор. Детерминированные правки без моделей. Что нельзя
   починить без сверки с изображением — записывается как находка.
4. Валидатор. Проверки по правилам (контрольные суммы, шаблоны, суммы
   таблиц, целостность таблиц). Каждая находка → запись в `report.json`.
5. Сверка (по флагу `--verify`). Второй прогон в режиме `pipeline`,
   нормализация, сравнение по абзацам. Расхождения → находки
   «низкая уверенность» с номером страницы.

Выход: `out.md` (подаётся в `convert.py` без изменений последнего),
`report.json` (правило, серьёзность, страница, фрагмент, предложение),
при `--annotate` — те же находки в markdown как callout-ы
`!! ПРОВЕРИТЬ: … !!` (существующий синтаксис конвертера);
`strip_annotations()` снимает их перед финальной выдачей.

## Принятые решения

- Отправка документов заказчиков в облако mineru.net допустима для всех
  документов. Файл проходит через CDN OpenXLab; токен API — JWT сроком
  около 90 дней, ротацию учитывать в эксплуатации.
- Движок — MinerU cloud, `model_version=vlm` (бейкофф: ~9/10 против
  5–6/10 у `pipeline`). OCRmyPDF остаётся локальным оффлайн-вариантом
  за тем же протоколом.
- vlm не байт-детерминирован: два прогона дают разный текст. Сравнения
  с эталонами и в `diff` — по порогу и после нормализации, не на точное
  равенство.
- Агент-потребитель — Hermes Agent на собственном хосте (Linux/WSL2).
  Точка подключения — CLI с JSON-выводом. HTTP-сервис не нужен.
- Сверка с изображением на первом этапе — человеком по пометкам.
  Vision-сверка (Gemini) — отдельный этап 9 за протоколом `Verifier`,
  только по помеченным фрагментам, по вырезке страницы.
- Отчёт: источник истины — `report.json`; пометки в markdown —
  производная, включаются флагом.
- HTML-таблицы MinerU конвертируются в pipe-таблицы в постпроцессоре;
  `convert.py` не трогать. `rowspan` — повтор текста в каждой строке,
  `colspan` — текст в первой ячейке, остальные пустые, факт объединения
  — в отчёт. Неразбираемая таблица остаётся как есть и помечается.
- Кэш хранит сырой ответ MinerU (zip + meta.json), ключ
  `sha256(pdf) + provider + model_version + версия схемы`. Бэкенды:
  локальная папка `.cache/ocr/` и Google Drive.
- Эталон `golden.md` собирается из `vlm.md` по списку известных дефектов
  (см. этап 0), не вручную с нуля.
- Замена MarkItDown на pymupdf4llm отложена: MinerU vlm одинаково
  работает по сканам и по PDF с текстовым слоем; PyMuPDF под AGPL;
  холодный билд. MarkItDown остаётся оффлайн-фолбэком в UI.

## Известные дефекты vlm (ТЗ на постпроцессор и валидатор)

Детерминированно чинится:
- `№` приходит как `No` (Noп/п, No1, No384-ФЗ) — систематически
- `°C` приходит как LaTeX `$C^{\circ}$`
- `PoE` местами кириллицей (`РоЕ`)

Требует сверки, только пометка:
- галлюцинация: «сыпучими» → «сыручими»
- подмена в марке: «IP-камерами» → «IR-камерами» (в одном месте из трёх)
- блок подписей разорван: должности отдельным списком, ФИО отдельным,
  часть транслитом (Таипов→Taipov, Нуреев→Hypeeb)
- пункт, разорванный между страницами, выходит тремя таблицами,
  у продолжений пустая первая ячейка (номер пункта потерян)

Наблюдение: расхождения между прогонами `pipeline` и `vlm` совпали
с местами дефектов — основа для этапа 6.

### Этап 1 — расширение контракта провайдера

Файл `pdf_core.py`. Датакласс `OcrResult`: `markdown: str`,
`content_list: list | None`, `pages: list[PageInfo]` (номер, был ли OCR,
есть ли текстовый слой, предупреждения), `provider: str`,
`model_version: str | None`, `raw_dir: Path | None`. Протокол
`OcrProvider` возвращает `OcrResult`. `OcrmypdfProvider` адаптируется,
отдаёт пустой `content_list`. `pdf_to_markdown_with_status` и
`ocr_auto_mode` меняются минимально, под новый тип.

Проверка: существующие тесты зелёные, новый тест на контракт
`OcrmypdfProvider`.

### Этап 2 — MineruProvider

Файл `ocr/mineru_provider.py`. Цикл API v4: запрос ссылки на загрузку →
PUT файла → создание задачи (`model_version`, `language=east_slavic`,
`is_ocr`) → опрос статуса с таймаутом → скачивание zip → распаковка в
`raw_dir` → сборка `OcrResult`. Ретраи с экспоненциальной паузой на 5xx.
Понятные ошибки: истёкший JWT, исчерпание приоритетной квоты.
Предпроверка лимитов до загрузки: 200 МБ, 200 страниц; дока MinerU
противоречива (600 в тексте лимитов, 200 в `-60006`), не сверено. Ключ из
`MINERU_API_KEY`.

Проверка: юнит-тесты на записанных ответах API без сети; один живой
smoke-тест под `live`. Прогон по `bakeoff.pdf` сравнивается с `vlm.md`
по порогу схожести.

### Этап 3 — кэш

Файл `ocr/cache.py`. Один интерфейс, два бэкенда: `local`
(`.cache/ocr/`) и `drive` через новый `drive_client.py`, вынесенный из
`app.py` (единственная разрешённая правка `app.py`). Хранить сырой zip

Проверка: раунд-трип на `local` в тестах; живой тест на Drive под `live`.

### Этап 4 — детерминированный постпроцессор

Файл `ocr/postprocess.py`, цепочка чистых функций, каждая с тестом:
1. HTML-таблицы → pipe на `html.parser` из стандартной библиотеки
   (правила rowspan/colspan — см. решения).
2. Склейка таблиц через разрыв страницы: соседние таблицы с одинаковым
   числом колонок и пустой первой ячейкой у продолжения объединяются,
   номер пункта восстанавливается из последней заполненной.
3. `No` → `№` по контексту (перед цифрой, «п/п», «-ФЗ»).
4. LaTeX-градус → `°C`.
5. Смешанные алфавиты внутри токена по словарю известных латинских
   сокращений (PoE, IP, SNR, ITV, VIDEOMAX, RS-485, IP68…) — известные
   чинятся, неизвестные только помечаются.
6. Транслит-детектор (латинский токен, фонетически похожий на русское
   слово) — только пометка.
7. Блок подписей — только пометка.
8. В конце — `markdown_cleanup.py`.

Проверка: `vlm.md` → постпроцессор → расхождений с `golden.md` не больше
метрики из этапа 0; известные детерминированные дефекты исчезли.

### Этап 5 — валидатор

Файл `ocr/validate.py`, чистые функции, на выходе список находок
(`rule`, `severity`, `page`, `snippet`, `suggestion`). Правила: ИНН 10/12
знаков с контрольной суммой; КПП по формату; ОГРН/ОГРНИП с контрольной
суммой; ГОСТ/ГОСТ Р/ТУ по шаблону; единицы измерения из белого списка;
марки весов по регуляркам семейств ВЕСТА-С, РЕУС-Д, ВЕКТОР-ДВ; сумма
строк vs строка «Итого»; целостность таблиц (число ячеек в строке,
пустые нумерационные ячейки).

Схема `report.json` фиксируется в спеке. Функции `annotate(md, report)`
и `strip_annotations(md)`.

Проверка: синтетические тесты на каждое правило; на фикстуре валидатор
обязан поймать все известные дефекты бейкоффа.

### Этап 6 — детектор расхождений (под флагом)

Файл `ocr/diff.py`. Второй прогон в режиме `pipeline` (через кэш),
нормализация обоих текстов (пробелы, `№`, регистр, пунктуация),
выравнивание по абзацам через `difflib`, расхождения → находки
`low_confidence` с номером страницы из `content_list`.

Проверка: на паре `pipeline.md` / `vlm.md` должны подсветиться
«сыручими», «IR-камерами», блок подписей.

### Этап 7 — CLI для агента

Файл `ocr/cli.py`, запуск `python -m ocr.cli` (или скрипт `pdf2md`):
`pdf2md вход.pdf --out папка --engine mineru|ocrmypdf --mode vlm|pipeline
[--verify] [--annotate] [--cache local|drive]`. Пишет `out.md`,
`report.json`, сырьё в кэш. В stdout — краткий JSON-итог. Коды выхода:
0 чисто, 2 есть критичные находки, 1 ошибка тракта. Описание команды —
в `CLAUDE.md` и `README.md` в формате описания инструмента для агента.

Проверка: прогон по `bakeoff.pdf` из чистого окружения на Linux
и Windows.
